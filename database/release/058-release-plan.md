# DISI 058 release plan: transaction-return bWAR evidence

This is evidence recovery, data only. It adds Baseball-Reference team-season bWAR for the four returned players of existing Dodgers trades whose
value was unknown only because their WAR was not loaded: Jon Garland, Jim Leyritz, Mudcat Grant and Zoilo Versalles. The rows are read from the
two archived captures 057 registered, and no source row is added. The existing interval-bounded value rules decide every value.
**KNOWN RETURN WAR != ATTRIBUTABLE SIGNING VALUE.**

**Not applied to production.** Applying it, merging the PR and any deploy need explicit owner approval. Production is at 057 (generation 13,
259/259), and 057 is frozen. Baseline `main` is `af8c9770ee6e270e586eb2fadb288030aa935bc0`.

## Rollback

`rollback-058.sql` runs in one guarded transaction. It refuses unless 058 is applied, and it refuses if later research depends on the 058 evidence
(a superseding fact, or another source's rows for the four). It then:

- **retracts** exactly the 91 active rows of the four on the 057 sources (the 032 guard forbids deleting a team-season fact);
- proves that the active rows are exactly the pre-058 rows (1934; the 54 057 rows still active), and that realized value (297.60 / 87), the three
  signings, both queues and the prediction layer are the pre-058 state;
- refreshes once (production 14 → 15).

The two 057 sources stay. **058 can be applied again after its rollback** (production 15 → 16): it inserts fresh active rows beside the retracted ones.

### Dependency on 057 (source sharing)

058 cites the two source rows 057 registered instead of registering the same files twice. The consequences, proven on PGlite and PostgreSQL 17:

- **rollback-057 is no longer available once 058 has been applied, even after rollback-058.** Its guard (released, hash-pinned `f78599ad…`)
  refuses when any row of a player outside its eleven, active or retracted, cites its sources ("later research depends on the 057 evidence"), and
  the ledger never deletes. The refusal changes nothing.
- **The frozen 057 is no longer independently rerunnable.** Its postconditions count every row on those sources ("145 active rows cite the 057
  sources; 54 were reviewed" while 058 is active; "a 057 row … belongs to a player outside the eleven" after rollback-058). The refusal changes
  nothing.
- 057 stays idempotent at its own release boundary; migration order is authoritative. Neither 057 file is modified.

**LOGICAL 058 ROLLBACK is not HISTORICAL MIGRATION ROLLBACK AVAILABILITY.** If 058 requires reversal, rollback-058 restores the logical pre-058
state (it retracts, never deletes, its 91 facts). However, once 058 has ever been applied, rollback-057 remains unavailable under its released
guards, because those retracted ledger facts keep citing the shared 057 sources. This limitation is known before release. No workaround is
attempted: no edit of released 057, no deletion of ledger facts, no duplicated provenance sources. **Production apply of 058 therefore requires
the owner's explicit acceptance of this historical rollback limitation.**

Rollback-058 is the only rollback available after the apply, and after it 057 cannot be rolled back by script. `rollback-050` was already unavailable after 057
(10 of its 11 players carry 057 rows). `rollback-055` and `rollback-056` are unaffected.

The release brief expected rollback-057 to become available again after rollback-058; the released rollback-057 guard does not allow that, and
changing it (or duplicating the sources) is outside this migration's scope.
