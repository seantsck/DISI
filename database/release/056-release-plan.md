## Order

1. Back up (`pg_dump` through the safe runner, mode 600, SHA-256 file; restore-verified on PostgreSQL 17: the verifier with
   `EXPECTATIONS_THROUGH_055` 258/258 on the restored copy; 056 applies, reruns, rolls back and reapplies on it).
2. Read-only, on production, before the apply: the HEAD verifier fails exactly the five moved pins (players_total 372, league_benchmark_players
   152, player_evaluations 155, scouting_legacy_ranks_total 163, scouting_legacy_ranks_backfilled 152); `EXPECTATIONS_THROUGH_055` is 258/258;
   Luis Rodriguez's Dodgers signing stores rank 4; the stored evaluation fingerprint is `67f2f80c...`; no 2019 population or coverage row exists;
   none of the 26 new MLB ids or slugs exists.
3. Apply `056_international_benchmark_2019.sql` through the safe runner (SHA-checked, `ON_ERROR_STOP`). One transaction, applied once; about 4 s
   plus one snapshot refresh.
4. Verify read-only: live verifier 258/258; catalog 79 / 156 / 37; generation 12 on all eleven snapshots, drift 0; the counts above; the Dodgers
   rows byte-identical (Luis Rodriguez 4); the 2013-2018 class hashes unchanged; benchmark reach 166 / 34 / 132; 2019 labels 4 / 22 with 26
   10-season rows censored; evaluation current at `86b58f47...`, no model supported; probabilities, expected values and recommendations 0.
5. Isolation: compare every table of the restored backup with live (only the 15 benchmark tables gain rows, no pre-existing row changes; the
   snapshots carry one refresh); schema and security fingerprints identical.
6. Merge the PR (normal merge commit, exact-head protection); the GitHub -> Vercel production deploy follows (no application change).
7. Smoke: `/league` (the 2019 sample listed, 30 / 26), `/prediction-readiness` (166 labelled; Dodgers targets not supported; no probability),
   `/players/luis-rodriguez-2019` (unchanged), `/players/jasson-dominguez` (a benchmark dossier), `/`, `/research`, `/methodology`,
   `/development`; HTTP 200, no "Data unavailable", none of the three unresolved players shown; the current deployment's logs clean.
8. Freeze on a bookkeeping-only branch (59 -> 60 frozen, `UNRELEASED_ADDITIONS = []`).

Do not re-apply 056 in production to test idempotency (proven on PGlite and PostgreSQL 17). If step 3 fails nothing is committed.

## Rollback

`rollback-056.sql` (one transaction, guarded: it refuses unless 056 is applied and refuses if later research depends on a 056 player) removes
exactly the 056 rankings (the 026 guards disabled inside the transaction only), players, signings, members, coverage row, population, audits,
outcomes and evidence, restores the 055 evaluation rows exactly, proves the Dodgers signings unchanged and the guards re-enabled, and refreshes
once. The sources stay as provenance. **056 can be applied again after its rollback.**
