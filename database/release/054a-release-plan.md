# DISI 054a release plan: development research-queue performance

A post-054 query-shape correction: `v_dodgers_development_research_queue` marks its `team_stints` CTE `NOT MATERIALIZED`. Same columns, rows,
grants, comment and `security_invoker` behaviour; no table, fact, function, index, policy, grant, contract or snapshot changes.
**Not applied to production.** Applying it, merging the PR and any deploy need explicit owner approval. Production is at 054 (generation 10,
258/258); 054 is frozen (PR #32, `7adf17c`).

## Why

The first `/development` request after the 054 freeze deployment (`dpl_CevApPP5vSR5SbUwVgnKxeNL7oTm`, 2026-10-25 02:19:36Z) logged
`DISI development fetch failed ... 57014 canceling statement due to statement timeout`: the anon role's statement timeout is 3 s. Measured
read-only on production as anon (2026-10-25):

| | 054 view (production today) | 054a query (the exact built text) |
|---|---|---|
| Execution | 1273-1376 ms (wall 1.45-1.69 s) | **54-55 ms** (wall about 0.18 s with the round trip) |
| Temp I/O | 687,810 temp blocks read (about 5.4 GB), 393 written | **0** (33,431 shared hits) |
| Plan | `CTE team_stints` materialized, rescanned per player | inlined; `player_season_stints_player_idx (player_id, season)` |
| Planning | 8.5-16.6 ms, 9.1 MB | 16.2-22.6 ms, 18.0 MB |
| Rows | 128, `a263c50069f8d139a681dae0e400432b` (whole rows) / `081f8efb25d47334b3727bcfd32149a1` (without the player id) | the same |

The 054 definition names `team_stints` about forty times, so PostgreSQL materializes it; with the hosted `work_mem` (2184 kB) the materialized
set spills to disk and every per-player subquery rescans it. Inlining `progression` as well measured the same and is not part of 054a.

## Guard and postconditions

The migration builds the 054 and the 054a queries as temporary views, so the server deparses all three definitions the same way on any
PostgreSQL version. It refuses unless 054 is applied and the live view is exactly the 054 definition (or already 054a, on a rerun) and
`security_invoker`. After the replace it proves the definition is the 054a one, the rows equal the 054 query's on the same database as a multiset
(`except all` both ways, and the count), the grants, options, comment and owner are unchanged, and no snapshot drifts.

## Order

1. Back up (`pg_dump`, restore-verified on PostgreSQL 17; the verifier 258/258 on the restored copy).
2. Read-only, on production, before the apply: the exact 054a query as anon returns `081f8efb25d47334b3727bcfd32149a1` (128 rows), like the
   live view, with no temp I/O.
3. Apply `054a_development_queue_performance.sql` through the safe runner (SHA-checked). One transaction; it reads the queue twice (about 3 s).
4. Verify: live verifier 258/258, drift 0, generation 10 on all eleven snapshots; the live view's row hash as above; `explain` as anon shows no
   `CTE team_stints` and no temp I/O.
5. **Four-concurrent-anon gate** (as for 045a): four sessions as anon (production `statement_timeout` 3 s), each reading
   `select * from public.v_dodgers_development_research_queue` three times at once (12 reads), through the transaction pooler (port 6543), read-only.
   Pass: 0 errors (no 57014), every read under 1 s, median recorded. Before 054a the single read already takes about 1.4 s.
6. Merge the PR (normal merge commit); one Vercel production deploy (no application change). Smoke `/development` (200, no "Data unavailable",
   104 gaps / 128 rows / 62 players) on the first request after the deploy, and the current deployment's logs (no 57014).

Do not re-apply 054a in production to test idempotency (proven on PGlite and PostgreSQL 17). If step 3 fails nothing is committed.

## Rollback

`rollback-054a.sql` (one transaction, guarded: it refuses unless the view is exactly the 054a definition) restores the 054 definition, proves the
same rows, unchanged grants, options, comment and owner, and drift 0. Nothing else is touched. **054a can be applied again after its rollback.**
