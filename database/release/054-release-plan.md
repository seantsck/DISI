# DISI 054 release plan: full-career transaction history

A new canonical career-history layer for a player's moves between clubs other than the Dodgers (one table, one view, one product-contract row), the
development research queue reading it for chronology, three read-only verifier checks, and the dossier, `/development` and methodology wording.
**Not applied to production.** Applying it, merging the PR and any deploy need explicit owner approval. Production is at 053 (generation 9,
255/255); 053 is frozen.

## Order

1. Back up (`pg_dump`, restore-verified on PostgreSQL 17; the through-053 verifier 258/258 on the restored copy).
2. Apply `054_full_career_transaction_history.sql` through the safe runner (SHA-checked). One transaction; about 19 s on PGlite.
3. Verify: live verifier 258/258, drift 0, generation 10 on all eleven snapshots, the counts above, the ledger byte-identical.
4. Merge the PR (normal merge commit); one Vercel production deploy. The application reads `v_player_career_transactions` tolerantly: against a
   pre-054 database it reads chronology from the Dodgers-ledger rows as before.
5. Smoke: `/development` (104 gaps; no "waits on a transaction"; the ledger/career-history note), `/players/carlos-santana` (2022, 2023, 2025,
   2026 as career history; 2008 the Dodgers trade), `/players/diego-cartaya` (2025: release then signing, career history), `/players/yasiel-puig`,
   `/players/juan-castro` (2008: overlapping appearances, for review), `/players/carlos-rincon`, `/players/pedro-baez`, `/players/edgar-leon`,
   `/players/jose-vizcaino`, `/asset-conversion` (unchanged), `/methodology`, `/prediction-readiness`.

Do not re-apply 054 in production to test idempotency (proven on PGlite and PostgreSQL 17). If step 2 fails nothing is committed.

## Expected verifier results

- Against production **before** applying 054: the candidate verifier fails exactly `public_tables_total` and `public_views_total` (78 / 155 against
  the head's 79 / 156); `EXPECTATIONS_THROUGH_053` is 258/258.
- **After** applying: **258/258**, drift 0, generation 10.

## Rollback

`rollback-054.sql` (one transaction, guarded: it refuses unless the table holds exactly the reviewed rows and nothing but the stream view and the
research queue depends on it) restores the 053 queue text, drops the view and the table, deletes the contract row and the two sources, and refreshes
the snapshots once. Every canonical table returns to its exact pre-054 content and the catalog to its pre-054 shape. **054 can be applied again
after its rollback** and reproduces the same content.
