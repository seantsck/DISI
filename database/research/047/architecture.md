# 047 architectural gap analysis

Written before any 047 schema decision. Result: **no schema change is necessary.** The existing model represents every fact 047 needs, so
047 adds research data, deterministic derivations in `lib/research/`, and product views, and nothing else.

## Reused structures

| Need (spec phase) | Existing structure | Used for |
|---|---|---|
| sourced chronology of development (1, 2) | `player_season_stints` (player / team / league / level / season, with source, as-of and retrieval) | affiliate assignment, level, season, games, age during season |
| development event model (2) | `development_milestones` + `development_event_codes` (`PROFESSIONAL_SIGNING`, `PROFESSIONAL_DEBUT`, `DSL_DEBUT` .. `AAA_DEBUT`, `MLB_DEBUT`, `FIRST_DODGERS_MLB_APPEARANCE`, `ORGANIZATION_CHANGE`, `RELEASED`, `RETIRED`) with date precision, season, evidence basis, confidence | SIGNED, FIRST_PRO_SEASON, LEVEL_REACHED, MLB_DEBUT, ORGANIZATION_EXIT |
| canonical / review status (2) | `development_progression_decisions` (`DEVELOPMENTAL_ARRIVAL`, `EARLY_CAMEO`, `POST_ESTABLISHMENT_APPEARANCE`, `REVIEW_REQUIRED`, with `PENDING_REVIEW`) | an ambiguous sequence is pending, never asserted |
| derived timing (10) | `v_dodgers_player_development_summary`, `disi_development_days / years`, `v_signing_records.years_signing_to_mlb` | signing-to-first-pro, signing-to-MLB, age at debut (derived, never stored) |
| transaction events and types (5) | `transaction_events` (`TRADE`, `RELEASE`, `FREE_AGENCY`, `FREE_AGENT_SIGNING`, `SALE`, `WAIVER`, `RULE5_SELECTION`, `EXPANSION_DRAFT`) with from / to organization, date, source | exits |
| assets and packages (5, 6) | `transaction_event_assets` (side, type, identity: MLB id, B-Ref id, cash, pool space), `transaction_asset_resolutions` (a player to be named later and its resolution) | package pieces, unresolved participants |
| uncertainty and conflict (5, 15) | `research_source_conflicts`, observation `confidence`, sealed `ACTIVE` / `RETRACTED` records | disagreements kept, nothing last-write-wins |
| control intervals and lineage (6, 7) | `v_player_control_intervals`, `v_transaction_asset_lineage`, `v_transaction_package_lineage` | later value generated by incoming pieces |
| attribution (7) | `product_player_decision` (042): direct Dodgers value, value elsewhere, individually attributable return, package participation, observable-not-attributable | the attribution states |
| the exit of the signing itself (3, 5) | `v_dodgers_international_exit_summary.control_state` | the `EXIT` dimension |
| queues (4, 14) | `v_dodgers_development_research_queue`, `v_transaction_research_queue`, `v_value_research_queue` | existing issue names are reused; no category is duplicated |

## Gaps found, and what 047 did about each

| Gap | Decision |
|---|---|
| no single completeness notion; a boolean would conflate different needs | six independent dimensions, derived in `development-research.js`; not stored |
| no ordered development queue | deterministic seven-tier ordering in `development-research.js`; the database queue still supplies the issues |
| `chain_status` was being read as the signing's own exit | documented and fixed: it describes the players the Dodgers *received*; the signing's own exit is the exit summary's `control_state` |
| `STILL_ACTIVE` read as "still with the club" | it means the signing was *traded* and a returned asset is still held; surfaced as `RETURN_STILL_ACCRUING` |
| no package completeness view | derived per trade from the existing queues (`packageCompleteness`); no new view |
| the first recorded season was treated as the first professional season | a record two or more seasons after signing is only the first *observed* record |
| exit types `RETIRED`, `CONTRACT_PURCHASE`, `LOST_ON_WAIVERS` are not transaction types | deferred: no 047 fact needs them, and unneeded event types are not added |
| no UI for development completeness or asset paths | `/development`, `/asset-conversion`, the dossier asset path, and evidence gaps on `/prediction-readiness`, all from relations the product contract already names |

## Why a new table or column would be wrong

- Completeness and attribution states are functions of canonical dates and snapshot rows; storing them would duplicate derivable facts and
  let them go stale.
- Time to MLB is a difference of two canonical dates.
- A development or transaction fact belongs in the existing sourced tables so provenance, sealing and retraction rules apply uniformly.
- Every table that would be exposed needs RLS, grants, policies and a Data API audit; none is needed.
